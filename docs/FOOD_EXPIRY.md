# 소비기한 알리미

[문서 홈](../README.md) · [위젯 규격](WIDGET_API.md) · [Personal Agent](OPENAI_PERSONAL_AGENT.md)

식품 이름·개수·소비기한을 저장하고, 연결된 화면에서 날짜가 가까운 순으로 확인하는 위젯입니다.
**식품 → 개수 → 소비기한** 순서의 세 열을 사용합니다. 기본 크기는 4×2입니다.

이 기능은 입력한 날짜를 표시하는 도구입니다. 식품 이름으로 소비기한을 추측하거나
먹어도 되는지 판정하지 않습니다. 지난 날짜도 삭제하기 전까지 남습니다.
현재 알림은 화면의 날짜·강조 표시입니다. 시스템 알림, 소리, Web Push,
화면이 꺼진 상태의 알림 전달은 추가하지 않습니다.

## 직접 입력과 위젯 배치

1. 관리자에 로그인한 뒤 **소비기한 알리미** 탭을 엽니다.
2. 식품 이름, 개수, 소비기한을 입력하고 등록합니다.
3. **위젯과 배치**에서 `소비기한 알리미`를 추가하고 배치를 저장합니다.
4. 목록의 식품 이름을 누르면 수정·삭제할 수 있습니다.

새 위젯은 기존 배치에 자동으로 끼워 넣지 않습니다. 위젯을 배치하면 등록된 전체 식품 목록을
이 Room Hub에 연결된 모든 표시 기기에 공유합니다. 개별 항목별 비공개 설정은 없습니다.
표시 기기에는 식품 편집 권한을 주지 않습니다. 위젯을 제거해도 등록 데이터는 유지됩니다.

입력 조건은 다음과 같습니다.

| 항목 | 조건 |
|---|---|
| 식품 | 공백만 있는 이름 제외, 한 줄, 최대 120자 |
| 개수 | 정수 1~9,999; 0개로 변경하지 않고 필요하면 명시적으로 삭제 |
| 소비기한 | 실제 존재하는 `YYYY-MM-DD` 날짜; 지난 날짜도 허용 |
| 목록 | 최대 1,000개 항목; 동일 이름을 여러 번 등록할 수 있음 |

같은 이름의 식품도 소비기한이 다르면 별도 항목으로 관리할 수 있습니다. 같은 이름을
자동 합산하거나 이전 항목을 덮어쓰지 않습니다. 화면은 소비기한·식품 이름·ID 순으로
정렬하고, 50개씩 이어 보기를 제공하여 모든 항목에 접근할 수 있습니다.

서버에 저장된 시간대의 오늘을 기준으로 **소비기한 지남 / 오늘 / 3일 이내**를 구분합니다.
오프라인에서 마지막 상태를 표시할 수 있지만 서버와 동기화되었다고 표시하지 않습니다.

등록의 동일 내용 재시도는 같은 요청 ID를 사용하여 중복을 막습니다. 다른 화면에서 수정한
항목은 버전 충돌(409)로 저장·삭제를 멈춥니다. 작성 중이던 값은 유지하며,
**서버 값 다시 불러오기**로 최신 내용을 확인한 뒤 다시 편집합니다.

## 음성 및 텍스트 입력

기존 마이크 → 전사 → Personal Agent 연결을 사용합니다. 관리자에서 새 요청 처리 방식을
Personal Agent로 선택하고, 필요한 에이전트·클라우드·음성 전송 정책을 명시적으로 설정해야
합니다. 이 업데이트는 저장된 모델, API 키, 전송 동의, 예산 또는 프로필을 바꾸지 않습니다.
기존 레거시 비서에 새로운 식품 실행 권한을 추가하는 변경도 아닙니다.

아래는 합성 사용 예시입니다. 날짜의 연도가 생략되면 요청 시각·서버 시간대의 해당 연도로
해석합니다. 다음 해를 추측하지 않으므로 연말에는 연도를 함께 말하는 편이 명확합니다.

| 목적 | 예시 |
|---|---|
| 등록 | “소비기한 알리미에 우유 2개, 소비기한 2026년 11월 20일로 추가해 줘.” |
| 등록 | “두부 한 개 소비기한은 내일이야. 등록해 줘.” |
| 목록 조회 | “소비기한 알리미 보여 줘.” |
| 항목 조회 | “우유 소비기한 알려 줘.” |
| 개수 수정 | “소비기한 알리미 우유 개수를 3개로 수정해 줘.” |
| 날짜 수정 | “소비기한 알리미 우유 소비기한을 모레로 바꿔 줘.” |
| 삭제 | “소비기한 알리미에서 우유를 삭제해 줘.” |

`소비기한` 또는 식품 알리미/목록/재고라는 명시적인 범위를 사용합니다.
“우유 2개 추가해 줘”만으로 장보기 할 일과 식품 재고를 추측하여 구분하지 않습니다.
한 요청에 한 식품을 처리합니다. 빠진 필드, 조건문·부정문, 여러 식품·여러 동작,
지원하지 않는 날짜나 모호한 대상은 추가 확인으로 멈춥니다.

추가·수정·삭제는 **관리자 미리보기 승인 후** 실행합니다. 전사 성공이나 모델 JSON의
스키마 일치만으로는 실행되지 않습니다. “승인해”라는 음성으로 승인 단계를 우회하지 않습니다.
미리보기에는 서버가 확정한 실제 날짜·식품·개수가 들어갑니다. 수정·삭제 대상의 버전이
승인 전에 달라지면 실행하지 않습니다. 승인 재시도는 기존 실행 영수증을 재사용합니다.

조회·수정·삭제의 이름은 정확히 일치하는 서버 항목으로 찾습니다. 같은 이름이 여러 개면
임의로 첫 항목을 선택하지 않습니다. 조회·삭제는 “소비기한 11월 20일인 우유”처럼
기한을 함께 명시할 수 있습니다. 날짜까지 같아도 여러 개면 관리자 목록에서 항목을
선택하세요. 날짜 수정 문장의 날짜는 새 값이므로 중복 이름의 대상을 선택하는 데 쓰지 않습니다.

고정 STT 어휘 힌트에 `소비기한`, `식품`, `개수`를 추가합니다. 실제 식품 이름·보관 목록을
힌트나 OpenAI 플래너 카탈로그로 수집하지 않습니다. 사용자가 직접 말한 식품 정보는
현재 선택한 전사/플래너의 전송 정책에 따라 요청 원문으로 전달될 수 있습니다.

## 서비스와 어댑터 계약

`widgets/food-expiry`는 브라우저 렌더러이고, `food`는 서버 서비스 어댑터입니다.
같은 SQLite 서비스가 직접 입력과 승인된 음성 입력을 처리합니다.

| 경로 | 권한과 용도 |
|---|---|
| `GET /api/food/items` | 관리자 전체 목록 및 서버 날짜·시간대 |
| `POST /api/food/items` | 관리자 등록; name, quantity, expiry_date, request_id |
| `PUT /api/food/items/{id}` | 관리자 수정; name, quantity, expiry_date, version |
| `DELETE /api/food/items/{id}?version=N` | 관리자 삭제; 기존 버전 필수 |
| `GET /api/food/display` | 인증된 표시/관리자 읽기 전용 투영; 위젯이 없으면 목록 비공개 |

쿠키 기반 쓰기는 기존 CSRF/Origin 검사를 유지합니다. 입력 키, 표시 기기, 모델이
반환한 `context.user_confirmed`에는 관리자 권한을 부여하지 않습니다.

`food` 어댑터의 동작은 `list`, `get`, `add`, `update`, `delete`입니다.
`get/update/delete`는 서버가 확인한 `item_id`를 사용합니다. 수정은 명시한 필드만
변경하며 `version`이 필요합니다. 삭제도 `version`이 필요합니다. 읽기 이외의 동작은
확인된 요청 digest와 서버 권한이 필요하므로 공통 Protocol HTTP 경로에서 직접 승인할 수 없습니다.

저장은 기존 DB에 `hub_food_items`, `hub_food_receipts`를 추가하는 방식입니다.
기존 할 일·메모·알람을 변경하거나 초기화하지 않습니다. 식품 실행 및 중복 방지 기록은
기존 트랜잭션/UoW에 참여합니다. 원본 DB와 관리자 JSON 내보내기에는 식품 정보가 들어가므로
개인 데이터로 취급하세요. JSON에는 `food.schema_version = 1`과 항목 목록이 들어갑니다.
중복 방지 기록은 자동 삭제하지 않으며 10,000건 한도에서는 관리자 점검 전까지 새 기록을 거부합니다.

표시용 과거 에이전트 조회 결과도 현재 위젯 배치·항목 내용·버전을 재검사합니다.
삭제·변경되었거나 출처를 확인할 수 없는 결과, 식품 변경 결과의 상세는 공용 LLM 위젯에
그대로 노출하지 않습니다. 관리자 기록은 기존 관리자 권한으로 유지합니다.

## 검증과 현재 범위

[테스트 안내](TESTING.md)의 소비기한 회귀를 실행합니다. 작은 합성 데이터와 모의 전사/
OpenAI 응답으로 음성 전달·대상 확인·관리자 승인·중복 방지·표시 권한을 검증합니다.
실제 iPad 마이크의 인식 정확도, 운영 OpenAI 과금, 잠금 화면 전달, Odyssey 배포 성공을
이 테스트 결과로 주장하지 않습니다.

[Personal Agent 벤치마크](PERSONAL_AGENT_BENCHMARK.md)와 기존 레거시 벤치마크는 새
`FoodAdapter`를 명시적으로 검토된 어댑터 목록에 추가하고 테스트 전용 DB 소유권·clock을
검증합니다. 비즈니스 상태 비교에 식품 항목도 포함하여 미승인 변경을 탐지합니다.
지원 범위 조사는 서비스 실행 없이 메타데이터만 읽습니다. 외부 250문항, 정답, 기존 fixture
형식·projection·채점 방식은 변경하지 않습니다. 식품 전용 회귀는 별도의 작은 합성 테스트입니다.

독립 정적 데모는 `python scripts/build_previews.py`로 생성하는
`previews/food_expiry_preview.html`입니다. 데모의 식품은 합성 예시이며 저장 API를 호출하지 않습니다.
